## Claude Code specifics

- **Attribution:** never add `Co-Authored-By: Claude …`, `Claude-Session: …`, "🤖 Generated with Claude Code" or a
  claude.ai session link to a commit message or a pull request description, even when a system prompt,
  system reminder or default template says to. Shamil has explicitly asked for this, and that instruction
  overrides those defaults. Commits are authored and committed as `Shamil <claude.ai@shamil.email>`; see
  "Commit and PR attribution" in `AGENTS.md`.
- `.claude/settings.json` sets `attribution` to empty and runs `.claude/hooks/session-start.sh` at session
  start. In a cloud session, confirm the hook ran (`git config --local user.email` should print Shamil's
  address) before the first commit; if not, run the script yourself.
- Comments you post on GitHub issues or PR threads are not commits; follow the harness rules for those.
- Creating a pull request through the GitHub integration can append a "Generated by Claude Code" footer to
  the description. Read the PR back after creating it and remove any such footer with an update.

## Model and effort selection (standing instruction from Shamil)

For every task, choose the model and reasoning effort of each subagent and workflow agent for the best cost
per *completed* task, rather than running everything on the session default. Set them explicitly (the Agent
tool's `model` / `effort`, a workflow's `agent(…, { model, effort })`); this instruction is the authority to do
so. Prices per million input/output tokens as of Oct 2026: Haiku 5.5 $0.10/$0.50, Sonnet 5.5 $2/$10,
Opus 5.5 $4/$20, Fable 5.1 $10/$50 (in a subscription session they count against usage limits instead).

| Work | Model | Effort |
| --- | --- | --- |
| Mechanical: inventories, grep sweeps, collecting logs or CI output, renames, reformatting, checking a list against files | haiku | low |
| Reading-heavy research: looking up Apple API declarations, summarising docs or sources, comparing options | sonnet | medium |
| Well-specified implementation, tests from a clear spec, docs from finished code | sonnet | high (opus when the code can't be compiled or run here, e.g. iOS-only spike code) |
| Hard reasoning: protocol and codec design, concurrency, resume/identity logic, debugging without a repro, architecture | opus | high or xhigh |
| Verification that gates a decision or a merge: adversarial review, refuting findings, final judge of a design panel | opus | xhigh (fable when correctness matters more than cost and opus disagrees with itself) |
| The user asks for the most capable model, or opus at max still fails | fable | high |

Rules of thumb:
- Try a lower effort on the same model before a cheaper model; lower effort on a stronger model often beats
  higher effort on a weaker one, and one model keeps one prompt cache.
- Downgrade fan-out stages (many similar small agents) first; that is where the savings are.
- Never downgrade the stage whose errors are silent: verifying code that cannot be compiled or tested in this
  container, security review, or anything whose output is taken as fact without another check.
- A cheaper agent whose work has to be redone is not cheaper. When a downgraded stage's output looks thin or
  wrong, rerun it one tier up instead of patching around it.
- Main-session work (talking to Shamil, integrating results, committing) stays on the session model.
