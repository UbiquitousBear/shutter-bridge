#### 1. How long to stay joined, and leaving from the background (decision 2, Iteration 3)

**Decided (Shamil, 8 Nov): (a), as recommended**, with the 3-minute stay in a single tunable constant; leaving from the background is tested in Iteration 3, week 1.

- **Options:** (a) one stay timer from the end of the import, running only while the app is in front; if the app goes to the background after the import, leave at once in the short background time iOS gives an app that has just left; if the import finishes in the background, leave as the last step of the continued task; on a return to the front, leave if the stay has run out. (b) The same stay, but while the app is suspended stay joined and leave on the next return to the front (the camera's Wi-Fi stays on and the phone stays on mobile data while the app is away: decision 2's option (b) drawback). (c) Keep the continued task running through the stay (untested; Apple documents expiry for tasks that report little progress). (d) No timer: stay while the camera's screen is open, with a *Leave now* button.
- **Recommended:** (a), with a 3-minute stay held in a single constant that Shamil sets; 3 minutes is a starting default, not a measured figure. Try to keep the app's Bluetooth link up during the stay, as in the 4 Nov run, and reconnect if it drops (it dropped by itself 11.2 s after a join on 5 Nov). A stay with the link down past 64 s is untested, so if the link can't be restored, leave or shorten the stay. Decision 8's hold on reminders while connected covers the whole stay, because the camera keeps advertising while our app holds a link (5 Nov 02:12:20). In Iteration 3, week 1, test removing the configuration from the background before relying on it.
- **Why:**
  - A joined phone kept the camera's Wi-Fi at status 2 for 785 s after CloseSession, through background spells and a 73 s lock, with the app's Bluetooth link up (4 Nov 12:39–12:54, one run). With the link closed, only 62.8–64 s has been tested (3 Nov 14:56 and 15:21, 4 Nov 13:06). Findings, *A phone that stays joined*.
  - The 3 Nov 23:18 and 23:51 copies started on a phone that was already joined, and the log has no join. ### 3.22 Data model: what "already imported" matches on (Shamil, 8 Nov, after the 17.1 bench run) · Data model and storage

**Current:** the `CameraObject` row of the *Data model and storage* table: "The diff ledger; `(camera, filename, captureDate, size)` is the uniqueness constraint".

**Proposed:** "The diff ledger. Each row records one copy: `(camera, folder, filename, captureDate, size)`, unique per store (the store enforces it, so the schema stays CloudKit-compatible). Whether a file is already imported is matched on `filename`, `captureDate` (to the second) and `size` alone, whatever the USB mode, the camera or the folder, so a file imported in MSC isn't imported again in MTP. Accepted risk: two cameras writing the same file name in the same second at the same size count as one." Add `folder` to the row's key fields. (The implementation also ignores ASCII case in the file name, which isn't part of Shamil's rule: for Shamil to confirm before it goes into the proposal.)

**Evidence:** the 17.1 bench run (8 Nov, q-mtp-browse failed: files imported in MSC weren't marked imported in MTP, because the two modes give different camera keys and folders); Shamil's decision the same day. The rule needed no schema change: every row already holds the name, date and size ([iteration-1-backlog.md](iteration-1-backlog.md), section 4). Still to check on the bench: that MSC and MTP report the same capture second and size for one file.
