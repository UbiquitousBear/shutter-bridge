## 0. Production workspace

The Swift Package Manager workspace from the proposal's project layout, created only after the go/no-go.

Acceptance criteria:

- Packages `PTPKit`, `CameraTransport`, `ImportEngine`, `Catalogue`, `PhotosBridge`, `AppUI` and the test-only `PTPSimulator`, each building and testing alone.
- Dependencies follow `AppUI → ImportEngine → {Catalogue, PhotosBridge, CameraTransport} → PTPKit`, with `PTPSimulator` depending on `PTPKit` only.
- Swift 6 language mode with strict concurrency in every package; Apple frameworks only.
- `PTPKit` moves in unchanged from `Packages/PTPKit/`. Nothing from `Spike/` is carried in; the spike stays archived in `Spike/`.
- The workspace is committed (not generated), so Xcode Cloud needs no post-clone step.
- The engine is transport-neutral from the start (spike-remaining.md, section 6): pause, continue, stall and retry are rules of the engine, not of `USBLink`, because the Wi-Fi link in Iteration 3 needs the same ones.

Could change with: the go/no-go itself. Wireless is in 1.0 (Shamil, 2 Nov) and the wireless row answered Go, so `IPLink` stays a 1.0 package in `CameraTransport`; it is built in Iteration 3, not now.

## 1. PTPKit

Done during the spike (`Packages/PTPKit/`; 133 tests pass with Swift 6.4.2 on Linux and macOS, 7 Nov; 143 on Linux, 8 Nov). The fixture tests skip until captures exist:

- PTP containers: encode and decode of command, data, response and event containers, sequences of containers, a transaction counter that wraps.
- Code tables: operations, responses, events, object formats, device properties, vendor extension, storage IDs, object handles. Sony vendor codes from libgphoto2 are marked unverified.
- Command builders: `GetDeviceInfo`, `OpenSession`, `CloseSession`, `GetStorageIDs`, `GetStorageInfo`, `GetNumObjects`, `GetObjectHandles`, `GetObjectInfo`, `GetObject`, `GetThumb`, `GetDevicePropValue`, `GetDevicePropDesc`, `GetPartialObject` and `GetPartialObject64`, MTP `GetObjectPropList` with a decoder for its reply (`MTPObjectPropList`, including the 128-bit `PersistentUniqueObjectIdentifier`), and Sony's `SDIO_Connect`, `SDIO_GetExtDeviceInfo`, `SDIO_OpenSession`, `SetContentsTransferMode` and the large partial read (0x9211) with its variants.
- Datasets with decode, encode and public initialisers: `DeviceInfo`, `StorageInfo`, `ObjectInfo`; storage ID and object handle arrays; PTP date-time parsing; media kind from extension or format code; pair stem; object identity (camera key, filename, capture date, size), with the true size passed in for objects of 4 GiB or more.
- `PTPPassThrough`: decodes `requestSendPTPCommand` replies in every layout Apple's documentation leaves open, and reports which one it saw.
- `PTPPartialRead`: chunk planning, 32- or 64-bit variant choice, the resume rule, 16 MiB checkpoints.
- PTP/IP framing, a stream decoder that never buffers a data phase, a transaction state machine, and responder-side encoders for tests and the simulator.
- Seeded round trips (7 Nov, PR #64): encode → decode identity for every container type, the datasets, the ID and handle arrays, PTP strings and date-times, PTP/IP packets, MTP property lists and the pass-through layouts, from a SplitMix64 generator with literal seeds. They found and fixed two codec bugs (a long string cut inside a surrogate pair; `PTPPartialRead.Chunk.end` overflowing near `UInt64.max`).
- A Sony whole-card session plan for Iteration 3 (7 Nov, PR #64): `SonyContentsTransferPlan`, `SonySessionRunner` and `SonyCapabilities`, pure and `unverified` until fixtures (iteration-3-4-backlog.md, section 1).
- Fixture tests, skipped until captures exist, for the kinds PTPKit decodes (DeviceInfo, ObjectInfo, StorageInfo, storage IDs, object handles, events; the DeviceInfo and ObjectInfo tests also check the round trip as a prefix), and a garbage-input test across every decoder.
- `PTPPassThrough` pinned to what ImageCaptureCore produced (8 Nov): `dataThenResponse`, tested with the shapes of 1 Nov's GetStorageIDs (8 B + 12 B, response transaction 801 for our 1) and 5 Nov's GetDeviceInfo (247 B + 12 B, 1677 for our 1); the four layouts it never produced stay behind their tests, so an unexpected one is decoded and logged rather than lost.
- Two empty pass-through values decode as `PTPPassThrough.Failure.noAnswer` (8 Nov), distinct from a malformed reply (`noResponseContainer`).
- `PTPFirmwareVersion` and `PTPDeviceInfo.firmwareVersion` (8 Nov): a firmware string carries its source (DeviceInfo, keyed by vendor extension, or a named non-PTP source such as Bluetooth's CC0A), and `compare` answers nil across sources, so MTP's "2.0" is never ordered against PC Remote's or Bluetooth's "2.01". PTPKit compared no versions before.

## 2. USBLink

The `CameraLink` implementation over `ImageCaptureCore`, in `CameraTransport`. Per the proposal, links are dumb pipes that answer list, info, thumb, bytes and events, and nothing else; each is an actor that owns its connection. The draft assumed one USB mode with PTP pass-through under every call. The findings show two modes that behave very differently, so the link branches on the transport type, not on `acceptsPTPCommands` (decision 7). Single runs unless the findings say otherwise; card type and cable aren't recorded in the findings yet.

| | Image Transfer (MSC) | Image Transfer (MTP) |
| --- | --- | --- |
| `ImageCaptureCore` sees | `ICTransportTypeMassStorage`; the device is named after the card's volume ("Untitled"); the card also mounts in Files | `ICTransportTypeUSB`, named ILCE-7CM2, as is Remote Shoot (PC Remote), which lists no files |
| PTP pass-through | None: `acceptsPTPCommands` says yes, but `GetDeviceInfo` and `GetStorageIDs` got no reply in 60 s and `GetObjectHandles` none in 120 s | Works, but every command waits until `ImageCaptureCore`'s catalogue has finished |
| Catalogue (listing) | 7.17 s for 391 files (12.23 s on the first run); 11.33–11.61 s for 547–549 (about 21 ms a file) | 64.96 s for 391; 82.14 s for 549; 122.72 s for 825 (149–166 ms a file); the percentage stays at 0 % and all files appear at the end |
| ARW, one at a time / two in flight (20 files, 839 MB) | 39.89 / 41.73 MB/s | 38.19 / 39.05 MB/s |
| JPG, one at a time (20 files, 440 MB) | 41.66 MB/s | 25.61 MB/s |
| `ImageCaptureCore` thumbnail | 187.56 ms each, one at a time (1 Nov) | 73.0 ms each two at a time, 80.8 ms one, 87.6 ms four (5 Nov); 144.8 and 148.1 ms one at a time on 1 Nov |
| Byte ranges | `requestReadData` at an offset untested; no `GetPartialObject` | `GetPartialObject` 0x101B (32-bit), verified with a cable pull; `requestReadData` also reads at an offset |
| Stable identifiers | Handles are 0 | Object handles and `PersistentUniqueObjectIdentifier` (16 B) are the same across sessions and after a replug; `ICCameraFile.ptpObjectHandle` is 0 (the 5 newest files logged, 1 Nov) |
| Events | None (no PTP) | None: `ObjectAdded` isn't advertised |
| Memory peak (baseline) | 71.03 MB (68 MB) | 70.04 MB (67 MB) |

Acceptance criteria:

- **Discover:** an `ICDeviceBrowser` with the "Cameras, local" mask (0x101), which found the camera in MSC, MTP and PC Remote, surfaces each camera as a `CameraDescriptor` (name, carrier, mode). Contents and control authorisation showed no prompt on iOS 27.2 and both returned `authorized` (the proposal's forum-report worry didn't appear). The mode comes from the transport type. Remote Shoot (PC Remote) also reports `ICTransportTypeUSB`, opens a session and completes its catalogue at once with 0 files; the app then asks for MSC or MTP (decision 1). Live Stream (USB Streaming) doesn't enumerate.
- **Open:** opens the session (0.00–0.04 s in the runs). In MTP it sends no PTP command until the catalogue has finished, since every command waits for it; in MSC it sends none at all.
- **List and info:** lists every file on the card from `ImageCaptureCore`'s own items (name, size, capture date), in both modes (listing over PTP is no faster in MTP and impossible in MSC), sorted newest first on the capture date. In MTP name, size and date matched `GetObjectInfo` for an ARW and a JPG; MSC has no `GetObjectInfo` to compare. The listing times in the table are the baseline; in MTP a catalogue left open survives an app relaunch while the camera stays plugged in (391 files in 0.09 s, against 65 s cold; a replug takes the full time again). In MSC the files appeared during the listing (40 to 387 files in 6 s on the 12.23 s run); whether the delegate delivers them as they arrive wasn't recorded, so check it in the first week.
- **Thumb:** `requestThumbnailData`, newest first, two requests in flight (decision 7): in MTP 73.0 ms each against 80.8 ms one at a time and 87.6 ms four at a time (one run each, 50 ARW each time; they still come back one at a time, 12–14 a second, so 60 take about 4.4 s). MSC two at a time isn't measured. The thumbnail is most likely the camera's 160 × 120 one (about 6–7 KB). The previews inside the files are slower, 429–435 ms per ARW (20 files) and 369 ms per JPG, so in MTP the grid doesn't read them unless it needs more than 160 px; MSC, where the card is a mounted file system, is untested. In MTP there is nothing to ask a thumbnail for until the catalogue ends.
- **Bytes:** `requestDownloadFile` per file into a folder the request names (the completion string is the file name), never holding the file in memory (memory peaked 3 MB over baseline in both modes). An interrupted file is copied again from its start after a replug (decision 7): an ARW restarts in about 1 s at 40 MB/s. No chunked `GetPartialObject` on USB in Iteration 1. A file of 4 GiB or more can't be read in ranges, but 1.0 is stills only.
- **Events:** an `AsyncStream` of what the browser reports: removal (`didRemove`, 30 ms after a failed read in MTP; 5.3 s after the *Continue* tap in the MSC pull), and the lifecycle callbacks below. No camera events arrive over USB in either mode.
- **Lifecycle:** reports *will suspend*, *did suspend*, *cancelled suspending* and *resumed operations*. *Did suspend* came 30.0–30.1 s after *will suspend* every time it was timed (MSC and MTP, with the app in the background and under lock, each time inside a continued task), and *resumed operations* 0.26–0.9 s after the app came back. Without a continued task the transfer stopped within about 2 s of the app leaving (at most the file in flight finished, within about 1.7 s; MSC, 2 Nov), and no *did suspend* timing was recorded then. A return within the 30 s cancels it. *Resumed operations* also fired with no suspension before it (two to five times a run), so the engine continues on the app's return, not on that callback alone. The session survived: 652 s of lock, the longest tried, and 144 s in another app.
- **Errors:** every failure maps to one of the engine's four outcomes (retry now, retry on reconnect, skip this file, stop the job). A cable pull ends every pending call with "retry on reconnect" and pauses, without failing the file in flight (decision 4); in the spike's MSC pull the file in flight failed with `ImageCaptureCore` error -9934 and the copy ended. A stalled download isn't a failure: the same `requestDownload` survived a 632 s suspension, yet the spike's 60 s limit failed three files. Pass-through requests stay well inside `ImageCaptureCore`'s limit of about 60 s, and an empty reply means "no answer". The engine never sends a whole-card `GetObjectPropList` (no answer in 60 s; after one such attempt the camera answered nothing until it was replugged).
- **Numbers on the bench iPhone** (USB 2, so the proposal's USB 3 target of ≥ 80 MB/s stays unmeasured): the 30 MB/s target holds for ARW in both modes (38–42 MB/s) and fails for JPG in MTP (25.6 MB/s); the plan's go/no-go floor of 25 MB/s is met everywhere. In the whole-card copies (stopped at 195 of 360 ARW in MSC and 217 of 362 in MTP), files ran at 41.8 MB/s with the app in front and 39.2 in the background in MSC (70 and 120 files), and at 38.7 and 37.8 MB/s in MTP (123 and 91 files); 360 ARW take about 6½ minutes at 40 MB/s. Listing times as in the table: 200 files isn't measured; the per-file cost implies roughly 4–6 s in MSC and 30–33 s in MTP (arithmetic, not a measurement). The camera shows as soon as the browser reports it; that delay wasn't timed, so record it on the bench.

Open points:

- **How to key the camera in MSC.** The draft took the serial from `GetDeviceInfo`, because `ICDevice.serialNumberString` is macOS-only, but MSC answers no PTP and names the device "Untitled". In MTP the device's UUID string embeds a 12-character string that looks like the camera's USB serial, so it is private data: if it is used as the key it is hashed and never logged or written to a fixture. Whether the MSC device's UUID (USB ID 0000:0000) carries it isn't recorded. In MTP `GetDeviceInfo` has the serial, but only after the catalogue (65–123 s). Settle in week 1 what key both modes can share (spike-remaining.md decision 7 names folder, name, capture date and size for the file, not the camera).
- **Telling MTP from Remote Shoot (PC Remote).** Both report `ICTransportTypeUSB`. What differs, from the findings: PC Remote's catalogue completes in 0.03 s with 0 files and its DeviceInfo lists 81 operations with Sony's extension (MTP: 24, none), but the rule isn't tested.
- **MSC identity after a replug.** The card is a mounted file system, so folder and name shouldn't change; that isn't tested after a replug.

Could change with: a bench result that contradicts a figure behind decisions 1, 4 and 7, which are decided (both modes stay, MSC recommended; the last-known card matters most in MTP, with 65–123 s listings); card type and cable (blank in the findings, so the throughput figures may move); a USB 3 iPhone (unmeasured); the *Select USB Connect Mode* behaviour on plugging in (the camera asks, unless the mode is fixed); whether MSC's thumbnails are quicker two at a time.

## 3. ImportEngine, happy path

The actor that runs discover, open, enumerate and diff, download and commit for one job. Its pause, continue and retry rules are transport-neutral (section 0).

Acceptance criteria:

- Imports a selection end to end through `USBLink` (or the simulator), into a temporary file per object, then `PhotosBridge`, then a catalogue row, then deletes the temporary file. When Photos access is denied, the destination is the Files folder instead (decision 9; section 5): the temporary file is moved into it, not copied (moving each file into place took about 0.01 s in the Wi-Fi copies of 3 Nov), and the row records where the file went. The engine takes the destination as a parameter, so the same pause, continue and retry rules apply to both.
- Downloads in flight on USB are a setting, 1 or 2. Two gained 2 % in MTP (39.05 against 38.19 MB/s) and 5 % in MSC (41.73 against 39.89), one run each, so the proposed default is 1 unless a bench run says otherwise. There are no PTP commands in the import path on USB (one path, decision 7), so there is nothing to serialise there.
- Progress as an `AsyncStream<ImportProgress>` (files done and total, bytes, MB/s, ETA), published at most 4 times a second, counted in bytes (decision 4). The rate leaves out a file that was in flight across a suspension or a pause: per-file rates after a return aren't throughput (the spike logged one file of 35.4 MB at 1745 MB/s).
- **Pause on *did suspend*, continue on return** (decision 1): when the link reports *did suspend* or the camera's removal, the engine pauses the job; on the app's return it continues in the same session, without reopening it when the session is still there. Iteration 1 runs no continued task over USB (below), and without one the transfer stopped within about 2 s of the app leaving (2 Nov); the 30 s to *did suspend* was timed only inside a continued task. So check in week 1 whether *did suspend* reaches the engine at all without one, and if it doesn't, pause when the app leaves the foreground instead. In the spike *Continue* found the files left in the open session and finished the first one 1.0–1.1 s after the tap.
- **A stall pauses and retries; "failed" is for real errors,** with a limited number of retries (decision 4). After a cable pull, once the camera is back and listed, the engine finds the files left by identity and copies the file in flight again from its start (decision 7).
- **A file that finishes suspiciously fast after a continue is checked.** The spike's first file after one took 0.02 s for 35.4 MB, most likely served from what `ImageCaptureCore` had already read; its size matched and it opened in Files, but its bytes weren't compared. The engine checks the size, and the hardware test compares the bytes.
- The engine keeps the screen on while a USB import runs (decision 1), and the Import screen says why. Not testable in the Simulator: it needs the bench iPhone.
- No `BGContinuedProcessingTask` over USB in Iteration 1: it buys at most 30 s there (decision 1). The proposal puts the continued task in Iteration 4; [iteration-3-4-backlog.md](iteration-3-4-backlog.md), sections 0 and 9, proposes building it at the start of Iterations 3 and 4 for Wi-Fi (spike-remaining.md, section 6, asks for it for Wi-Fi; Shamil decides the split).
- A file that is already imported, by identity, is not queued again.

## 5. PhotosBridge with RAW+JPEG pairing and the Files-only destination

Acceptance criteria:

- Creates assets with `PHAssetCreationRequest` from file URLs, never from data in memory.
- RAW+JPEG pairing, with the default rule: same folder, same stem, capture time within 1 s. An `.ARW` and a `.JPG` or `.HIF` that match become one asset: the JPEG or HEIF as `.photo`, the ARW as `.alternatePhoto`. A lone ARW, JPEG or HEIF becomes its own asset (the newest ARW on the card on 1 Nov had no JPG of the same name). **The rule is untested on the camera's data,** although the pairs are on the card: on 5 Nov it held 539 ARW and 286 JPG, and Photos' own Import listed 539 items, so each pair is one item there; in MSC a frame's two files sit in the same folder under the same stem (about 44–48 MB and 22–26 MB). Run the rule against that card in the first week.
- The camera's capture date (and GPS from EXIF, if present) is set on the asset. The PTP date has no zone; `PTPDateTime` reads it in the phone's current zone, as Photos does for the same EXIF value, which is unverified against this camera.
- Asks for `.readWrite` access once, at the first import, and works with `.limited` (decision 9). The prompt's text says that *Limit Access* with no photos selected is enough. The spike showed that add-only access saves a photo (0.2 s) but can't create an album without bringing up the read/write prompt anyway (spike-findings.md, "Photos albums"), so the proposal's `.addOnly` no longer holds, and "Verify imports against Photos" needs no separate permission.
- **Photos denied: import to Files, say so, link to Settings** (decision 9, Shamil, 7 Nov). When access is denied (*Don't Allow* at the prompt, or *None* in Settings), the import still runs and writes to a folder in Files. The Files-only path's criteria follow below; it is a scope addition to Iteration 1, because the proposal's 1.0 list has none.
- **Check the access level before an import, not after a failed save** (the *Don't Allow* run, 8 Nov, fresh install, iOS 27.3 beta). With add-only and read/write both declined, every save failed at once with PHPhotosErrorDomain 3311 (`accessUserDenied`), with or without an album, and asking for read/write again returned *denied* in 0.0 s with no prompt: iOS asks once. Acceptance: the import reads `PHPhotoLibrary.authorizationStatus(for: .readWrite)` before it starts and again before a paused or interrupted import continues (changing access in Settings means leaving the app, which pauses a USB import, and iOS usually ends an app whose Photos access changes: developer reports, untested here); `.denied` goes to the Files-only path below with the Settings link (`.restricted` too, if the proposal under *Trigger* is accepted). A 3311 from a save during an import counts as a denial, not a failed file: that file and the rest go to the Files folder with the same message and Settings link (the Import screen offers no destination choice, below). The spike saw 3311 only with access already denied before the save. Untested: read/write declined with add-only not yet asked (the product's own case: would a save then bring up the add-only prompt?), and add-only allowed with read/write declined; the status check keeps the app from relying on add-only either way.
- Puts each import in an album: creates it the first time, stores its `localIdentifier`, finds it by that identifier (the title can match more than one album), and checks `canPerform(.addContent)` before adding. With Limited Access it created the album with no prompt (0.2 s), found it by identifier after a cold relaunch and saved into it, and saved photos joined the limited selection by themselves.
- Stages downloads as complete-until-first-unlock (the default), never `complete` (decision 9): a locked save took 0.1 s, about 26 s after the lock, inside a continued task, with full access (K1; a locked save under Limited Access wasn't run). A `complete` file fails while locked (`PHPhotosErrorDomain` 3302). Over USB the app is in front for any long import, so this matters most for the 30 s after it leaves and for Iteration 3's background imports.
- Returns the `localIdentifier`, which the catalogue stores.
- Tested against a protocol, with a fake library in unit tests and the real one in the hardware plan.
- Albums are the user's choice, defaulting to one per camera (Shamil, 1 Nov). The options are one per camera, one per import (dated), or both.
- For a RAW+JPEG pair, the original is the user's choice, defaulting to RAW (Shamil, 1 Nov). Set it with iOS 27's `PHAssetCreationRequest.originalResourceChoice`, which only applies to RAW+JPEG assets. This replaces the fixed JPEG-as-`.photo` pairing in the criterion above; check how the choice maps onto the `.photo` and `.alternatePhoto` resources.

Files-only import path (decision 9), acceptance criteria. The spike's *Copy all RAW to Files* is the evidence: it wrote ARW (the run copies ARW only) into the app's Documents folder, and the files opened in Files (Shamil: the 49 copied before the 4 Nov MSC cable pull, and every file of the Wi-Fi copies, whole cards of 360 of 360). Over USB no copy reached a whole card (stopped at 195 of 360 in MSC and 217 of 362 in MTP), at the rates in section 2 (MSC 41.8 MB/s in front and 39.2 in the background; MTP 38.7 and 37.8); memory wasn't recorded in those copies (section 3), and `requestDownloadFile` peaked 3 MB over baseline in the 20-file runs.

- **Trigger:** Photos authorisation is denied, whether *Don't Allow* at the first prompt or *None* in Settings (treating `.restricted` by parental controls the same is proposed; decision 9 doesn't say, and it is untested). *Limited Access* is not a denial: those imports go to Photos (above).
- **Destination:** a folder in the app's Documents folder, shown in Files under On My iPhone › the app, as the spike's was. The Info.plist needs `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace`, which the spike's project sets (`Spike/project.yml`). The files are the camera's originals, byte for byte, never held in memory. No album, no pairing and no original choice apply: both files of a RAW+JPEG pair are kept, under their own names. The spike made a new folder for each copy; the folder layout for 1.0 (one per camera, as the album default, or one per import) is a week-1 choice, and Shamil decides if it matters.
- **It says so:** the Import screen states that photos are going to Files because Photos access is off, and names the folder, from the first file. A button opens the app's page in Settings to grant access. When the person comes back with access granted, the next import goes to Photos and files already in Files stay where they are (proposed; decision 9 doesn't say).
- **Done means:** after an import of 100 files (50 RAW+JPEG pairs) with Photos denied, every file is in the folder, opens in Files, and has the size the camera listed (the spike checked size and opening, not bytes; the hardware test also compares the bytes of the first file after a continue, section 3); an interrupted file is copied again from its start, and a name already in the folder is never overwritten. Whether to set the files' dates to the capture date, so Files sorts them by it, is a week-1 check; the spike didn't.
- **Same rules as Photos:** the import pauses on *did suspend* and continues on return, and the app stays in front (decisions 1 and 4), in MSC and in MTP (decision 7). Tested with a fake destination in unit tests and the real Files folder in the hardware plan; the Photos denial itself needs a fresh install on the bench iPhone.
- **Open, for Shamil:** whether Files is also offered as a chosen destination when Photos is allowed. Until decided, Files is only the denied-case fallback and the Import screen offers no destination choice.

Could change with: the filenames and pair stems in the captured ObjectInfo fixtures (an ARW and a JPG only, so no HEIF pair has been seen: whether the card holds HEIF pairs is open); whether Apple's RAW decoder handles the α7C II's ARW (not tested in the spike; thumbnails fall back to the embedded JPEG either way).

## 7. PTPSimulator v1

A fake camera for the integration suite, depending on `PTPKit` only.

Acceptance criteria:

- Serves a scripted card (N objects with sizes, dates and formats, including RAW+JPEG pairs) over PTP/IP on loopback, with a `Network.framework` listener, using PTPKit's responder encoders and dataset initialisers.
- Answers `GetDeviceInfo`, `OpenSession`, `CloseSession`, `GetStorageIDs`, `GetStorageInfo`, `GetObjectHandles`, `GetObjectInfo`, `GetThumb`, `GetObject` and `GetPartialObject` (0x101B, as over USB in MTP), and can send `ObjectAdded`. The real camera sends none over USB; over Wi-Fi it sends Sony's 0xC201 with a buffer-slot handle, not 0x4002.
- Its `DeviceInfo` and `ObjectInfo` are seeded from the captured α7C II fixtures, so it answers like the camera. They wait on the Mac (section 1). The two DeviceInfo flavours differ (MTP: 24 operations, no Sony extension, 5 properties, 3 events; PC Remote over PTP/IP: 81 operations, Sony's extension, no properties, 48 events), so say which one the simulator imitates.
- Runs in the iOS Simulator over loopback, so CI needs no camera.
- Open point: Iteration 1 has no `IPLink`, so the engine needs a way to reach the simulator, either a minimal test-only PTP/IP `CameraLink` (the spike's `PTPIPClient` is a starting point) or an in-process `CameraLink` over the scripted card. The findings add a reason to favour the in-process link for some tests: the behaviours the engine must handle (the 30 s suspension, a catalogue that blocks everything until it ends, no PTP in MSC, a cable pull) come from `ImageCaptureCore`, which a PTP/IP link can't reproduce. An in-process link that scripts *will suspend*, *did suspend*, *resumed operations*, a removal and a slow catalogue lets the engine's pause, continue and retry rules be unit-tested without hardware. Faults (drops, slow link, duplicate filenames) come in Iteration 2.

Could change with: the fixtures it replays; the operations the camera actually lists in DeviceInfo. Answered: over PTP/IP the camera doesn't take the standard `GetPartialObject` in a contents-transfer session (0x101B answers InvalidObjectHandle) and resumes with Sony's 0x9211, which the simulator adds in Iteration 3 together with the whole-card session (a plain session answers StoreNotAvailable).
