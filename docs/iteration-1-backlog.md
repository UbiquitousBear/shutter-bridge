Decisions taken here:

- **The project is hand-written and committed, not generated.** XcodeGen would need a post-clone step in Xcode Cloud (as the spike's does), which the criterion above rules out. The project uses Xcode 16's format (objectVersion 77) with a synchronized folder for `App/ShutterBridge/`, so the project file never lists source files and rarely changes; code goes in packages, not the app target.
- **The `canImport` rule.** Every package builds and tests on Linux: Apple-only frameworks (ImageCaptureCore, SwiftData, Photos, SwiftUI, Network) sit behind `#if canImport(...)`, so the transport-neutral logic is unit-tested on Linux with fakes and the Apple code is compiled and tested by CI in the iOS Simulator.
- **The GitHub Actions checks are kept** (section 8): `ptpkit.yml` became `packages-linux.yml`, every package on Linux; `app.yml` builds the app and runs every package's tests in the iOS Simulator; `spike-build.yml` stays as it is until the spike is retired, and `testflight.yml` uploads the production app by default from 8 Nov, with the spike still selectable (section 8).
- **Provisional, for week 1:** `CaptureDate` keys identity on the camera's wall-clock time, recovered from ImageCaptureCore's `Date` in the phone's zone at listing time, so a change of time zone doesn't make every file new; section 4 still decides it. The engine fixes the zone for a job at its start (an autoupdating zone would follow a change mid-job and give Browse's items new identities: `anAutoupdatingZoneIsFixedForTheJob`). That is right for items Browse listed before a change, but a relisting after one (a replug in another zone) dates its files in the new zone, so its identities no longer match. Neither a frozen nor an autoupdating zone is right for both: `CameraItem` should carry the zone the link made its dates in, or the raw wall-clock time (sections 2 and 4). `CameraItem.folder` is empty where a link can't tell, until section 4's MTP check.

## 1. PTPKit

Done during the spike (`Packages/PTPKit/`; 133 tests passed with Swift 6.4.2 on Linux and macOS on 7 Nov, and 167 pass with the camera's fixtures on Linux, 8 Nov):

- PTP containers: encode and decode of command, data, response and event containers, sequences of containers, a transaction counter that wraps.
- Code tables: operations, responses, events, object formats, device properties, vendor extension, storage IDs, object handles. Sony vendor codes from libgphoto2 were marked unverified; the ones the fixtures prove are settled (8 Nov, below).
- Command builders: `GetDeviceInfo`, `OpenSession`, `CloseSession`, `GetStorageIDs`, `GetStorageInfo`, `GetNumObjects`, `GetObjectHandles`, `GetObjectInfo`, `GetObject`, `GetThumb`, `GetDevicePropValue`, `GetDevicePropDesc`, `GetPartialObject` and `GetPartialObject64`, MTP `GetObjectPropList` with a decoder for its reply (`MTPObjectPropList`, including the 128-bit `PersistentUniqueObjectIdentifier`), and Sony's `SDIO_Connect`, `SDIO_GetExtDeviceInfo`, `SDIO_OpenSession`, `SetContentsTransferMode` and the large partial read (0x9211) with its variants.
- Datasets with decode, encode and public initialisers: `DeviceInfo`, `StorageInfo`, `ObjectInfo`; storage ID and object handle arrays; PTP date-time parsing; media kind from extension or format code; pair stem; object identity (camera key, filename, capture date, size), with the true size passed in for objects of 4 GiB or more.
- `PTPPassThrough`: decodes `requestSendPTPCommand` replies in every layout Apple's documentation leaves open, and reports which one it saw.
- `PTPPartialRead`: chunk planning, 32- or 64-bit variant choice, the resume rule, 16 MiB checkpoints.
- PTP/IP framing, a stream decoder that never buffers a data phase, a transaction state machine, and responder-side encoders for tests and the simulator.
- Seeded round trips (7 Nov, PR #64): encode → decode identity for every container type, the datasets, the ID and handle arrays, PTP strings and date-times, PTP/IP packets, MTP property lists and the pass-through layouts, from a SplitMix64 generator with literal seeds. They found and fixed two codec bugs (a long string cut inside a surrogate pair; `PTPPartialRead.Chunk.end` overflowing near `UInt64.max`).
- A Sony whole-card session plan for Iteration 3 (7 Nov, PR #64): `SonyContentsTransferPlan`, `SonySessionRunner` and `SonyCapabilities`, pure; its DeviceInfo gate is checked against the camera's two DeviceInfo fixtures (8 Nov), and the commands' parameters stay `unverified` (iteration-3-4-backlog.md, section 1).
- Fixture tests for the kinds PTPKit decodes (DeviceInfo, ObjectInfo, StorageInfo, storage IDs, object handles, events), and a garbage-input test across every decoder. They skip when no capture is in the bundle.
- **Golden tests pass on the camera's bytes (8 Nov, from Shamil's zip):** of 21 fixtures, 20 decode and re-encode to identical bytes and `sdio-extdeviceinfo.bin` has a structural check; PTP/IP StorageInfo asserts capacity 0.
- `PTPPassThrough` pinned to what ImageCaptureCore produced (8 Nov): `dataThenResponse`, tested with the shapes of 1 Nov's GetStorageIDs (8 B + 12 B, response transaction 801 for our 1) and 5 Nov's GetDeviceInfo (247 B + 12 B, 1677 for our 1); the four layouts it never produced stay behind their tests, so an unexpected one is decoded and logged rather than lost. `passThroughGolden` decodes the two captured data phases (`usb/deviceinfo.bin`, `usb/storageids.bin`) in that layout, each with a synthesised response (8 Nov).

- `PTPFirmwareVersion` and `PTPDeviceInfo.firmwareVersion` (8 Nov): a firmware string carries its source (DeviceInfo, keyed by vendor extension, or a named non-PTP source such as Bluetooth's CC0A), and `compare` answers nil across sources, so MTP's "2.0" is never ordered against PTP/IP's or Bluetooth's "2.01". PTPKit compared no versions before. `firmwareModes` passes on the two DeviceInfo fixtures (8 Nov): USB in MTP reports "2.0" with 0xFFFFFFFF and PTP/IP (captured 5 Nov, in a guided run whose setup has PC Remote Function off) "2.01" with 0x11, and the two never compare, so those two notes lost `unverified`; PC Remote's 0x11 and "2.01" (Wi-Fi 2 Nov, USB 4 Nov) stay log-only and `unverified`; CC0A's "2.01" keeps it (no Bluetooth fixture is committed).

## 2. USBLink

The `CameraLink` implementation over `ImageCaptureCore`, in `CameraTransport`. Per the proposal, links are dumb pipes that answer list, info, thumb, bytes and events, and nothing else; each is an actor that owns its connection. The draft assumed one USB mode with PTP pass-through under every call. The findings show two modes that behave very differently, so the link branches on the transport type, not on `acceptsPTPCommands` (decision 7). Single runs unless the findings say otherwise; card type and cable aren't recorded in the findings yet.

Acceptance criteria:

- **Discover:** an `ICDeviceBrowser` with the "Cameras, local" mask (0x101), which found the camera in MSC, MTP and PC Remote, surfaces each camera as a `CameraDescriptor` (name, carrier, mode). Contents and control authorisation showed no prompt on iOS 27.2 and both returned `authorized` (the proposal's forum-report worry didn't appear). The mode comes from the transport type. Remote Shoot (PC Remote) also reports `ICTransportTypeUSB`, opens a session and completes its catalogue at once with 0 files; the app then asks for MSC or MTP (decision 1). Live Stream (USB Streaming) doesn't enumerate.
- **Open:** opens the session (0.00–0.04 s in the runs). In MTP it sends no PTP command until the catalogue has finished, since every command waits for it; in MSC it sends none at all.
- **List and info:** lists every file on the card from `ImageCaptureCore`'s own items (name, size, capture date), in both modes (listing over PTP is no faster in MTP and impossible in MSC), sorted newest first on the capture date. In MTP name, size and date matched `GetObjectInfo` for an ARW and a JPG; MSC has no `GetObjectInfo` to compare. The listing times in the table are the baseline; in MTP a catalogue left open survives an app relaunch while the camera stays plugged in (391 files in 0.09 s, against 65 s cold; a replug takes the full time again). In MSC the files appeared during the listing (40 to 387 files in 6 s on the 12.23 s run); whether the delegate delivers them as they arrive wasn't recorded, so check it in the first week.
- **Thumb:** `requestThumbnailData`, newest first, two requests in flight (decision 7): in MTP 73.0 ms each against 80.8 ms one at a time and 87.6 ms four at a time (one run each, 50 ARW each time; they still come back one at a time, 12–14 a second, so 60 take about 4.4 s). MSC two at a time isn't measured. The thumbnail is most likely the camera's 160 × 120 one (about 6–7 KB). The previews inside the files are slower, 429–435 ms per ARW (20 files) and 369 ms per JPG, so in MTP the grid doesn't read them unless it needs more than 160 px; MSC, where the card is a mounted file system, is untested. In MTP there is nothing to ask a thumbnail for until the catalogue ends.
- **Bytes:** `requestDownloadFile` per file into a folder the request names (the completion string is the file name), never holding the file in memory (memory peaked 3 MB over baseline in both modes). An interrupted file is copied again from its start after a replug (decision 7): an ARW restarts in about 1 s at 40 MB/s. No chunked `GetPartialObject` on USB in Iteration 1. A file of 4 GiB or more can't be read in ranges, but 1.0 is stills only.
- **Events:** an `AsyncStream` of what the browser reports: removal (`didRemove`, 30 ms after a failed read in MTP; 5.3 s after the *Continue* tap in the MSC pull), and the lifecycle callbacks below. No camera events arrive over USB in either mode. Events are live (the `CameraLink.events` contract, 8 Nov): each read of `events` gets only what happens after it, nothing buffered from before, so a suspension and return while Browse had the link don't pause an import started later (`eventsFromBeforeTheJobDoNotPauseIt`). `USBLink` keeps one continuation per subscriber rather than one unbounded stream made at discovery: `EventFanOut` (pure Swift, so tested on Linux: subscribe-then-send delivers, a send before the subscription doesn't, two subscribers both get it, a subscriber whose reader has gone is dropped, finish ends every stream and later reads) fans each event out to every live stream, in order; every stream finishes after `.removed` (the link can't be used again; the browser hands out a fresh one) and on `close()`.
- **Lifecycle:** reports *will suspend*, *did suspend*, *cancelled suspending* and *resumed operations*. *Did suspend* came 30.0–30.1 s after *will suspend* every time it was timed (MSC and MTP, with the app in the background and under lock, each time inside a continued task), and *resumed operations* 0.26–0.9 s after the app came back. Without a continued task the transfer stopped within about 2 s of the app leaving (at most the file in flight finished, within about 1.7 s; MSC, 2 Nov), and no *did suspend* timing was recorded then. A return within the 30 s cancels it. *Resumed operations* also fired with no suspension before it (two to five times a run), so the engine continues on the app's return, not on that callback alone. The session survived: 652 s of lock, the longest tried, and 144 s in another app.
- **Errors:** every failure maps to one of the engine's four outcomes (retry now, retry on reconnect, skip this file, stop the job). A cable pull ends every pending call with "retry on reconnect" and pauses, without failing the file in flight (decision 4); in the spike's MSC pull the file in flight failed with `ImageCaptureCore` error -9934 and the copy ended. A stalled download isn't a failure: the same `requestDownload` survived a 632 s suspension, yet the spike's 60 s limit failed three files. Pass-through requests stay well inside `ImageCaptureCore`'s limit of about 60 s, and an empty reply means "no answer". The engine never sends a whole-card `GetObjectPropList` (no answer in 60 s; after one such attempt the camera answered nothing until it was replugged).
- **Numbers on the bench iPhone** (USB 2, so the proposal's USB 3 target of ≥ 80 MB/s stays unmeasured): the 30 MB/s target holds for ARW in both modes (38–42 MB/s) and fails for JPG in MTP (25.6 MB/s); the plan's go/no-go floor of 25 MB/s is met everywhere. In the whole-card copies (stopped at 195 of 360 ARW in MSC and 217 of 362 in MTP), files ran at 41.8 MB/s with the app in front and 39.2 in the background in MSC (70 and 120 files), and at 38.7 and 37.8 MB/s in MTP (123 and 91 files); 360 ARW take about 6½ minutes at 40 MB/s. Listing times as in the table: 200 files isn't measured; the per-file cost implies roughly 4–6 s in MSC and 30–33 s in MTP (arithmetic, not a measurement). The camera shows as soon as the browser reports it; that delay wasn't timed, so record it on the bench.

- **`USBCameraBrowser`** (actor; Apple-only): asks for contents and control access (`notAuthorised` if contents is denied or restricted; *not determined* is let through, as iOS 27.2 showed no prompt), browses with "Cameras, local" (0x101), and reports `USBDiscoveryEvent.appeared(CameraDescriptor)` and `.disappeared(id)`. - **Concurrency:** both actors run on the main actor's executor, because the spike drove ImageCaptureCore only from the main thread; the delegates are `Sendable` objects holding only an `AsyncStream` continuation, with `nonisolated` callbacks that yield `Sendable` signals in order to their actor, which owns all state. Each request is finished exactly once (completion, time limit, cancel, removal or close; `PendingCalls`). The one `@unchecked Sendable` is a box that hands an ImageCaptureCore device from the browser delegate's callback to the browser (safe because the callback reads nothing from it and keeps no reference once it has yielded it) and from the browser to a link, both on that same executor.

The phone out of space stops the job, whether the error says so itself or underneath ImageCaptureCore's own (the `NSUnderlyingErrorKey` chain; a full phone is untested, and the link doesn't check free space before a download as the spike did). The other ImageCaptureCore codes come from the SDK headers and are marked `unverified`. A cancel comes back as `busy` with the detail "cancelled". Stalled downloads never fail.

## 3. ImportEngine, happy path

The actor that runs discover, open, enumerate and diff, download and commit for one job. Its pause, continue and retry rules are transport-neutral (section 0).

Acceptance criteria:

- Imports a selection end to end through `USBLink` (or the simulator), into a temporary file per object, then `PhotosBridge`, then a catalogue row, then deletes the temporary file. The destination is Photos or the Files folder, by the destination setting, and Files whenever Photos access is denied or restricted (decision 9; section 5): for Files the temporary file is moved into the folder, not copied (moving each file into place took about 0.01 s in the Wi-Fi copies of 3 Nov), and the row records where the file went. The engine takes the destination as a parameter, so the same pause, continue and retry rules apply to both.
  **Done (8 Nov), in the engine with fakes:** `ImportEngine.start(_:from:camera:to:)` lists, diffs by identity, copies each file into its own folder under the staging folder, commits it (Photos, or the Files folder, which moves it), writes an `.imported` row with the asset identifier or the file's relative path, and removes what is left of the temporary file (`importsEverySelectedFile`, for Photos and for Files: the moved files have the listed size and bytes, staging ends empty). The route (`ImportRoute`) is built by the caller from section 5's `DestinationDecision` (`PhotosAccessGate.decision(for:)`, or `resolve(setting:authorisation:)`; `routeFollowsTheDecision`), with a reader of the Photos authorisation; `.askForPhotosAccess` never reaches the engine: the app asks first, and a route built from it throws `ImportEngineError.photosAccessNotAsked` (`aRouteNeedsPhotosAccessAskedFirst`). A 3311 mid-import (`.photosAccessDenied`) sends that file and the rest to Files and fails no file, with the reason from `DestinationDecision.afterDeniedSave(authorisation:)` read then: `photosDenied` with the Settings link (`photosDenialMidImportSwitchesToFiles` with 1 and 2 in flight; `bothFilesInFlightDeniedSwitchOnce`, where both files in flight are refused by Photos and the route switches once), or `photosRestricted` without it (`photosRestrictedMidImportSwitchesWithoutTheSettingsLink`, `afterADeniedSaveTheReasonFollowsTheAccess`); `resume(to:)` and `reconnect(_:to:)` take a new route after access is read again (`resumeCanChangeTheRoute`, `reconnectCanChangeTheRoute`). The engine hands the destination one `CommitUnit` per file for now (`commitUnit(for:)`, the seam section 5's pairing replaces; the diff already puts a RAW next to its JPEG). Through `USBLink` and the simulator it comes with sections 2 and 7.
- Downloads in flight on USB are a setting, 1 or 2. Two gained 2 % in MTP (39.05 against 38.19 MB/s) and 5 % in MSC (41.73 against 39.89), one run each, so the proposed default is 1 unless a bench run says otherwise. There are no PTP commands in the import path on USB (one path, decision 7), so there is nothing to serialise there.
  **Done (8 Nov):** `ImportSettings.downloadsInFlight`, read at the start of each job (`updateSettings(_:)` applies from the next); the download loop is a task group bounded by it (`downloadsInFlightFollowsTheSetting` with 1 and 2, `settingsApplyFromTheNextJob`).
- Progress as an `AsyncStream<ImportProgress>` (files done and total, bytes, MB/s, ETA), published at most 4 times a second, counted in bytes (decision 4). The rate leaves out a file that was in flight across a suspension or a pause: per-file rates after a return aren't throughput (the spike logged one file of 35.4 MB at 1745 MB/s).
  **Done (8 Nov):** `progress` publishes at most once per 250 ms on the injected clock, the last update of a job included (`progressIsPublishedAtMostFourTimesASecond`, `theLastUpdateOfAJobIsFlushed`, `throttleRules`); `ImportProgress` carries files done and total, bytes, MB/s, ETA, skipped and failed counts, the state and the destination with its reason. The rate is the bytes of the last 8 clean files over the union of their times; a file in flight across a pause or after an abandoned attempt is left out (`rateLeavesOutAFileInFlightAcrossAPause`, `rateEstimatorUnion`). Bytes done never go backwards: a file whose download restarts (stall, removal, retry) holds its place until the new attempt passes it (`bytesDoneNeverGoesBackwards`).
- **Pause on *did suspend*, continue on return** (decision 1): when the link reports *did suspend* or the camera's removal, the engine pauses the job; on the app's return it continues in the same session, without reopening it when the session is still there. Iteration 1 runs no continued task over USB (below), and without one the transfer stopped within about 2 s of the app leaving (2 Nov); the 30 s to *did suspend* was timed only inside a continued task. So check in week 1 whether *did suspend* reaches the engine at all without one, and if it doesn't, pause when the app leaves the foreground instead. In the spike *Continue* found the files left in the open session and finished the first one 1.0–1.1 s after the tap.
  **Done (8 Nov):** *did suspend* pauses (`appInBackground`); nothing new starts, and the download in flight carries on and is committed if it finishes (decision 4). The app continues the job with `resume(.appInBackground)`, which never lifts a pause the person made; *resumed operations* alone does nothing, and the session isn't reopened (`didSuspendPausesUntilTheAppReturns`, `appReturnDoesNotLiftAPersonsPause`). The week-1 fallback is ready: `pause(.appInBackground)` from the app's scene phase. **Needs the bench iPhone:** whether *did suspend* reaches the engine at all without a continued task.
- **A stall pauses and retries; "failed" is for real errors,** with a limited number of retries (decision 4). After a cable pull, once the camera is back and listed, the engine finds the files left by identity and copies the file in flight again from its start (decision 7).
  **Done (8 Nov):** no byte progress for 30 s while running is a stall: the attempt is abandoned (a late file is discarded), the job pauses (`stalled`) and the file is tried again with a fresh call 5 s later, three times by itself, then the job waits for the person; never "failed" (`aStallPausesThenRetriesTheFile`, `repeatedStallsWaitForThePerson`). The count is per file: progress on an attempt restarts the 30 s but not the count, which only the person continuing resets, so a file that always stalls part-way still waits for the person (`stallsThatEachMakeSomeProgressStillWaitForThePerson`). An abandoned call's task is cancelled, not awaited (`anAbandonedDownloadIsCancelled`): a link that honours cancellation (`IPLink`) stops the transfer, but one that ignores it (ImageCaptureCore) can still have the abandoned call in flight beside the retry, so the link may briefly see one call more than the downloads-in-flight setting. Real errors follow `FailureOutcome`: retry now (3 retries at 0.5, 2 and 5 s, then failed), retry on reconnect, skip this file, stop the job (`everyLinkFailureFollowsItsOutcome` over every kind, `transientFailuresAreRetriedALimitedNumberOfTimes`, `skipThisFileGoesOnWithTheRest`, `stopTheJobKeepsWhatWasImported`, `listingFailuresFollowTheirOutcome`); a failure of a call in flight across a pause doesn't count (`aFailureOfACallInFlightAcrossAPauseIsNotCounted`). Removal (the event or a `disconnected` failure, in either order) abandons the downloads, deletes their partial files and waits; `reconnect(_:to:)` opens and lists the camera again, finds the files left by identity and copies the interrupted one from its start (`cablePullPausesAndTheInterruptedFileIsCopiedAgain`, `aFileMissingAfterReplugIsSkipped`, `aDisconnectedFailureActsAsARemoval`). A removal that leaves nothing to copy (the cable pulled during the last commit) completes the job instead of waiting for the camera (`aRemovalDuringTheLastCommitStillCompletes`).
- **A file that finishes suspiciously fast after a continue is checked.** The spike's first file after one took 0.02 s for 35.4 MB, most likely served from what `ImageCaptureCore` had already read; its size matched and it opened in Files, but its bytes weren't compared. The engine checks the size, and the hardware test compares the bytes.
  **Done (8 Nov):** every downloaded file's size is checked against the listing (a stat costs nothing); a mismatch deletes it and downloads it again on the retry budget (`suspiciouslyFastFileAfterAContinueIsSizeChecked`). **Needs the bench iPhone:** comparing the bytes of the first file after a continue.
- The engine keeps the screen on while a USB import runs (decision 1), and the Import screen says why. Not testable in the Simulator: it needs the bench iPhone.

  **Done (8 Nov):** the engine uses none.
- A file that is already imported, by identity, is not queued again.
  **Done (8 Nov):** identity is camera key, folder, name, capture date and size (`CameraItem.identity(camera:timeZone:)`, public so Browse badges by the same rule), diffed with one `states(of:)` call; all-new and a date range queue `.new` and `.partial` rows, newest first, and an explicit pick queues anything not imported (`alreadyImportedFilesAreNotQueued`, `aDateRangeTakesOnlyItsFiles`, `pickedFilesThatCantBeImportedAreCountedAsSkipped`).
- Files added from Browse while a job runs are appended to it.
  **Done (8 Nov):** `append(_:)` adds them at the end, leaving out files already in the job or imported, and returns how many it added (`filesAddedDuringAJobJoinIt`). Cancel abandons the downloads in flight and removes their temporary files at once; a late file is discarded (`cancelRemovesTemporaryFiles`). A file being committed when its job ends (cancel or stop) finishes in its own task, which ending the job doesn't cancel, and records its row (`aCommitInFlightWhenTheJobEndsIsNotCancelled`); a job started straight away waits for that row before its diff, and `append` does too, so the file isn't saved twice (`cancelThenStartDoesNotSaveAFileTwice`). Catalogue writes go through the `CatalogueStore` actor and the engine has no main-actor code, which is structural rather than something a test can show; a catalogue that can't be read or written stops the job (`aCatalogueThatCannotWriteStopsTheJob`).

Decisions taken here (8 Nov, building section 3):

- **The numbers:** progress at most every 250 ms; a stall is 30 s with no byte progress while running (about ten times a healthy still, half of ImageCaptureCore's roughly 60 s command limit), counted from the attempt's start when the link reports none; a stalled file is tried again after 5 s, three times by itself (per file, until the person continues), then the job waits for the person; real errors get 3 retries at 0.5, 2 and 5 s (listing too); a catalogue write is tried twice before the job stops; the rate is measured over the last 8 clean files.
- **A pause doesn't cancel the download in flight** (the same request survived a 632 s suspension in the spike); it is committed if it finishes. **A stall abandons the call and asks again** with a fresh one; the abandoned call's task is cancelled but not awaited, and a late file from it is deleted, never committed.
- **A failure of a call that was in flight across a pause doesn't count** against the file's retries.
- **Only `.imported` rows are written.** `.partial` and resume offsets are Iteration 2's (decision 7 restarts a file over USB); the diff still queues `.partial` rows.
- **Files without a capture date are skipped** (they have no identity) until section 4 decides what to do with them.
- **API changes from the workspace PR:** `start` takes the camera key (the link can't supply it; section 2) and an `ImportRoute` (section 5's `DestinationDecision`, the destination, the Files folder for a 3311 mid-import, and a reader of the Photos authorisation for that case's reason); `append` is async (it asks the catalogue) and returns the count; `pause(_:)`, `resume(_:to:)`, `reconnect(_:to:)` and `updateSettings(_:)`; `currentProgress` and `isUSBImportRunning`; `ImportProgress` gains state, destination, skipped, failed and the USB flag (defaulted); `JobOutcome.catalogueUnavailable`; `ImportEngineError` loses `notBuilt` and gains `cameraNotRemoved`, `catalogueUnavailable` and `photosAccessNotAsked` (no client switches on these yet). `CameraLink.events` keeps its signature but its contract is tightened: events are live, never replayed to a later subscriber (section 2, *Events*). PhotosBridge's API is section 5's as merged (`DestinationSetting`, `FilesReason`, `DestinationDecision`), unchanged; `ImportProgress.destination` is that `DestinationDecision`, so the Import screen's Settings link is `destination?.filesReason?.offersSettingsLink`. CameraTransport gains `EventFanOut` (internal), which `USBLink` uses for the tightened contract.

- whether *did suspend* reaches the engine without a continued task (if not, the app calls `pause(.appInBackground)` from its scene phase);
- the screen staying on during a USB import;
- a 100-file import (50 RAW+JPEG pairs) in MSC and in MTP, to Photos and to Files, with the memory peak against the 150 MB budget;

## 5. PhotosBridge with RAW+JPEG pairing and the Files destination

Acceptance criteria:

- Creates assets with `PHAssetCreationRequest` from file URLs, never from data in memory.
- RAW+JPEG pairing, with the default rule: same folder, same stem, capture time within 1 s. An `.ARW` and a `.JPG` or `.HIF` that match become one asset: the JPEG or HEIF as `.photo`, the ARW as `.alternatePhoto`. A lone ARW, JPEG or HEIF becomes its own asset (the newest ARW on the card on 1 Nov had no JPG of the same name). **The rule is untested on the camera's data,** although the pairs are on the card: on 5 Nov it held 539 ARW and 286 JPG, and Photos' own Import listed 539 items, so each pair is one item there; in MSC a frame's two files sit in the same folder under the same stem (about 44–48 MB and 22–26 MB). - Asks for `.readWrite` access once, at the first import, and works with `.limited` (decision 9). The prompt's text says that *Limit Access* with no photos selected is enough. The spike showed that add-only access saves a photo (0.2 s) but can't create an album without bringing up the read/write prompt anyway (spike-findings.md, "Photos albums"), so the proposal's `.addOnly` no longer holds, and "Verify imports against Photos" needs no separate permission.

- **Check the access level before an import, not after a failed save** (the *Don't Allow* run, 8 Nov, fresh install, iOS 27.3 beta). It works on any `PairableFile` (folder, name, date), so the engine's camera items can conform without PhotosBridge depending on `CameraTransport`; `PairingUnit.map` turns a unit of camera items into the `CommitUnit` of its staged files. Tested with the PTP/IP fixtures' pair (DSC01779.ARW and .JPG, same parent and second), a wrapped counter, HEIF, case and a synthetic card shaped like 5 Nov's (539 ARW, 286 JPG → 539 units, 286 pairs). Still to do in week 1: run it against the real card's listing.
- **Destination setting** (`DestinationSetting`, a `Codable` value, default Photos; leniently decoded, so an unknown stored value reads as Photos) and **the rule** (`DestinationDecision.resolve(setting:authorisation:)`): the setting on Files → Files, chosen, whatever the authorisation (no Settings link, and never asks for Photos: granting access wouldn't send anything to Photos, *It says so*); with the setting on Photos, denied → Files with the Settings link, restricted → Files without it, Photos for Limited or full access, and *ask first* when not determined. `FilesReason` (chosen, Photos denied, Photos restricted) gives `offersSettingsLink` and a default British English line for the Import screen. `afterDeniedSave(authorisation:)` sends the rest of an import to Files after a 3311, with the reason read from the authorisation then. Persisting the setting is AppUI's (a later PR); nothing here touches `UserDefaults`.
- **Access** (`PhotosAccessGate`, tested with a fake library): reads `.readWrite` before an import and again before a continue, asks only while it is not determined and the setting says Photos (so once), and treats Limited as enough.
- **Files destination** (`FilesFolderDestination`, pure Foundation, tested with temporary directories on Linux): Documents/*camera name* (made safe: no separators, control characters or leading dots, at most 64 characters, "Camera" if empty, "Inbox" renamed because iOS keeps Documents/Inbox); each staged file is moved, never copied; a name already present (compared case-insensitively, including a file the person put there) is never overwritten: the file becomes "NAME (2).EXT" and the returned location records the name used; when either file of a pair clashes both take the same number, so the pair keeps one stem; the modification date is set to the capture date; if the second file of a pair can't be placed the first is moved back to staging; returns paths relative to Documents. Two cameras with the same name share a folder (the week-1 detail above is still open).
- **Photos destination logic** (`PhotosLibraryDestination` over the `PhotoLibraryClient` protocol, tested with a fake library on Linux): one asset per unit, from file URLs (`AssetCreation`); a pair keeps the proposal's layout, the JPEG or HEIF as `.photo` and the ARW as `.alternatePhoto`, with the person's original choice (default RAW) as the asset's `originalResourceChoice`, and a lone file has none (Apple documents setting it on a single-original asset as an error); the capture date as the creation date; the position from EXIF (`GPSLocation(exifGPS:)`, pure and tested; read from the JPEG or HEIF first, then the ARW); albums per `AlbumPlan` (one per camera by default, per import, or both), each found by its stored `localIdentifier` (`AlbumIdentifierStore`, which the app persists; an in-memory one is provided), created once and stored, made again if the person deleted it, and skipped and noted, not replaced, when `canAddContent` is false; the staged files are deleted after a successful save and left in place after a failure, so the Files fallback can move them. Error mapping (`ImportDestinationFailure(photoLibraryFailure:)`): 3311 and 3310 are a denial, not a failed file (also when creating the album); 3305 is no room; 3303 or a missing file is a staged file gone; anything else, 3302 included, is rejected with the domain and code. Staging protection: `StagingProtection.prepareDirectory(_:)` and `apply(to:)` give complete-until-first-unlock (iOS only; no-ops elsewhere), and the Photos destination lowers a `complete` file before a save.
- **Real library, compiled by CI only** (`SystemPhotoLibrary` behind `#if canImport(Photos)`, `ImageIOMetadataReader` behind `#if canImport(ImageIO)`): the calls the spike's `PhotosProbe` ran on iOS 27.2 and 27.3 (`authorizationStatus(for: .readWrite)`, `requestAuthorization(for:)`, `fetchAssetCollections(withLocalIdentifiers:)`, `canPerform(.addContent)`, one `performChanges` block per asset with `PHAssetCreationRequest.addResource(with:fileURL:options:)`), plus `creationDate`, `location`, the resource's original file name and type (from the camera's extension, since the staged file's own name may not carry it: ARW, JPG/JPEG, HIF/HEIF and HEIC mapped by name in `Resource.knownTypeIdentifier`, others only when `UTType` declares them, never a dynamic type) and iOS 27's `originalResourceChoice`. **How the choice maps onto the resources** (checked against Apple's documentation and the iOS 27 SDK diff, 8 Nov): the type is `PHAsset.OriginalResourceChoice` with `.compressed` (0) and `.raw` (1); the property "selects whether the RAW or the compressed resource serves as the original" of a RAW+JPEG asset, which reads as independent of the `.photo` and `.alternatePhoto` roles, so the layout above stays and only the choice changes. **Unverified:** that `.raw` with the ARW as `.alternatePhoto` makes the ARW the base for renders on the device.

## 7. PTPSimulator v1

A fake camera for the integration suite: the `PTPSimulator` target depends on `PTPKit` only; `SimulatedLink` adds `CameraTransport`, and the package's integration suite the engine (below).

Acceptance criteria:

- Serves a scripted card (N objects with sizes, dates and formats, including RAW+JPEG pairs) over PTP/IP on loopback, with a `Network.framework` listener, using PTPKit's responder encoders and dataset initialisers.
  **Done (8 Nov):** `PTPIPSimulatorServer` (behind `#if canImport(Network)`): an `NWListener` restricted to the loopback interface on a port the system picks, one actor pumping each TCP connection into `PTPIPResponderCore`, a pure core that does the Init_Command / Init_Event handshake (connection numbers, Init_Fail *busy* for a second initiator, Init_Fail for an event channel with the wrong number), Cmd_Request, the responder's data phases as Start_Data, Data and End_Data a packet at a time (`DataPhasePackets`, 1 MiB by default, so a 40 MB object never sits in memory), Ping and Pong, and an initiator data phase swallowed. Losing the command channel ends the session and closes the event channel. The core is tested on Linux against an initiator built from PTPKit's `PTPIPStreamDecoder` and `PTPIPTransaction`, in memory, with requests fed in 5-byte pieces (`PTPIPResponderCoreTests`, 10 tests, among them `listsTheCardOverPTPIP`); the server is tested in the iOS Simulator by `PTPIPServerTests.aClientListsTheCard`, a small PTP/IP client on `NWConnection` that does the handshake, lists the card, reads an object and a range byte for byte and receives an ObjectAdded, and `injectedResponsesReachTheClient` (both skipped on Linux; checked here only against a stub of Network's API, since no Mac took part).
- Answers `GetDeviceInfo`, `OpenSession`, `CloseSession`, `GetStorageIDs`, `GetStorageInfo`, `GetObjectHandles`, `GetObjectInfo`, `GetThumb`, `GetObject` and `GetPartialObject` (0x101B, as over USB in MTP), and can send `ObjectAdded`. The real camera sends none over USB; over Wi-Fi it sends Sony's 0xC201 with a buffer-slot handle, not 0x4002.
  **Done (8 Nov):** `PTPResponder`, pure: a command container in, an optional data phase and a response out, each operation only if the flavour's DeviceInfo lists it, everything but the first three only in a session (SessionNotOpen otherwise, SessionAlreadyOpen with the open ID, InvalidParameter for session 0). GetObjectHandles filters by store and format; a parent filter answers ParameterNotSupported, since no folder objects are served. GetThumb answers NoThumbnailPresent for a format with no captured template. GetPartialObject takes ISO 15740's three parameters (length 0xFFFFFFFF to the end) and returns the bytes sent as its response parameter; Sony's four-parameter variant isn't served. Anything else, listed or not (GetNumObjects, the MTP property operations, Sony's SDIO operations), answers OperationNotSupported. Object bytes are deterministic (`ScriptedCard.content(of:in:)`: byte *i* of handle *h* is (i + 7919 *h*) mod 251), so any range is produced alone and a copy is checked without keeping one; thumbnails are as long as the captured ones, between JPEG markers, and not decodable. Shooting more frames (`ScriptedCard.shootMore`, numbering, folder and dates continued) returns the events to send: ISO 15740's ObjectAdded (0x4002) with the new handle in the MTP flavour (the real camera sends none over USB; the simulator sends it so an initiator's handling can be tested), and the camera's own 0xC201 with transaction ID 0xFFFFFFFF and the buffer slot 0xFFFFC001 in the PTP/IP flavour, byte for byte the packet in `ptpip/event-objectadded.bin`. Faults: `inject(_:forNext:times:)` answers the next commands of an operation with any response code (`PTPResponderTests`, 11 tests).
- Its `DeviceInfo` and `ObjectInfo` are seeded from the captured α7C II fixtures, so it answers like the camera. They are committed (section 1). The two DeviceInfo flavours differ (MTP over USB, `usb/deviceinfo.bin`: 24 operations, no Sony extension, 5 properties, 3 events; PTP/IP, `ptpip/deviceinfo.bin`: 81 operations, Sony's extension, no properties, 48 events, the same counts PC Remote logged on 2 Nov), so say which one the simulator imitates.
  **Done (8 Nov):** **it imitates MTP over USB by default** (`SimulatorFlavour.usbMTP`), because Iteration 1 imports over USB and 0x101B behaves there as the section asks; `.ptpIP` swaps in the PTP/IP DeviceInfo and StorageInfo (capacity and free space 0, as sent) and Sony's ObjectAdded, but not the Wi-Fi behaviour (below). PTPKit's fixture copies are a resource of its *test* target, which no other package can reach, so the simulator bundles its own byte-for-byte copies (`Sources/PTPSimulator/Fixtures/`, whose README names each source): both DeviceInfos, both StorageInfos, and the USB ARW and JPG ObjectInfos, whose thumbnail and pixel fields every ARW and JPG on a scripted card borrows (160 × 120 JFIF thumbnails of 6,584 and 7,376 B, 7008 × 4672; a HIF borrows the JPG's as a placeholder, since no HIF is captured). Serials were already zeroed, and the pre-commit hook checks the copies as it checks every `*deviceinfo.bin`. `CapturedFixtureCopyTests` decodes every copy and compares each with its source in `Fixtures/a7c2/` where the checkout is reachable, so a later export that replaces a source fails it.
- Runs in the iOS Simulator over loopback, so CI needs no camera.
  **Done (8 Nov), to be confirmed by CI:** `app.yml` runs the `PTPSimulator-Package` scheme (every test target) in the iOS Simulator. Loopback also keeps the listener clear of the local-network permission on a device.
- Open point: Iteration 1 has no `IPLink`, so the engine needs a way to reach the simulator, either a minimal test-only PTP/IP `CameraLink` (the spike's `PTPIPClient` is a starting point) or an in-process `CameraLink` over the scripted card. The findings add a reason to favour the in-process link for some tests: the behaviours the engine must handle (the 30 s suspension, a catalogue that blocks everything until it ends, no PTP in MSC, a cable pull) come from `ImageCaptureCore`, which a PTP/IP link can't reproduce. An in-process link that scripts *will suspend*, *did suspend*, *resumed operations*, a removal and a slow catalogue lets the engine's pause, continue and retry rules be unit-tested without hardware. Faults (drops, slow link, duplicate filenames) come in Iteration 2.
  **Decided and done (8 Nov): the in-process link, as a second target of this package.** `SimulatedCameraLink`, in the target and product `SimulatedLink` (`PTPSimulator` + `CameraTransport`), conforms to `CameraLink` over a `ScriptedCard`: `holdCatalogue()` makes `list()` wait until `releaseCatalogue()`; `appLeavesForeground()`, `suspend()`, `cancelSuspending()` and `resumeOperations()` send *will suspend*, *did suspend*, *cancelled suspending* and *resumed operations*, and while suspended every call but `info(of:)` (which reads the cached catalogue, as `USBLink`'s does) waits and every download stops at its next chunk; `remove()` sends `.removed`, ends pending calls with `.disconnected` (leaving a partial file, as ImageCaptureCore can), finishes the events and leaves the link unusable, as `USBLink` is (so does `close()`: a closed link can't be opened again), and `replugged()` is a new link over the card as it is then with new item IDs; downloads write the scripted bytes into the folder given, a chunk at a time with progress; `script(_:_:)` makes a file's next call fail, deliver short or hold part-way until `release(_:)`; `fail(_:with:times:)` injects any `CameraLinkFailure` kind into open, list, info, thumbnail or bytes; cancellation is ignored as ImageCaptureCore ignores it, unless `honoursCancellation` (as `IPLink` will), which ends a call held part-way, waiting out a suspension or waiting for the catalogue at once with `noAnswer`; Remote Shoot lists no files (`.modeListsNoFiles`); events are live, never replayed (`SimulatedCameraLinkTests`, 16 tests). **Why here:** `PTPSimulator` itself still depends on `PTPKit` only, as the rule says, and the bridge to `CameraTransport` is a separate target in the same test-only package, so no production package names the simulator and every arrow points from test support to production code. A `CameraTransportTesting` product inside `CameraTransport` would have put a test-support product in a shipping package and made `CameraTransport` depend on the simulator (or carry its own fake card). The cost: this package now depends on `CameraTransport` and, for the integration suite only, on `ImportEngine`, `Catalogue` and `PhotosBridge`, so the documented rule now reads "the `PTPSimulator` *target* depends on `PTPKit` only; the package is a test-only leaf above the production graph" (section 0's line should say so when it is next edited). Nothing was ported from the engine's private test fakes: they script steps on a manual clock, and this link scripts the camera.
  **The integration suite (8 Nov):** `IntegrationTests` in this package (it lives here for now; other packages may still take `PTPSimulator` or `SimulatedLink` as a test dependency, since SwiftPM accepts a package cycle with no target cycle, which is to be confirmed in Xcode before relying on it there; `AppUITests` takes both products, section 6) runs the real `ImportEngine` on the continuous clock, through its public surface only, with the in-memory catalogue and the real `FilesFolderDestination` in a temporary Documents folder (Photos isn't reachable in a package test): the whole card imported with every file's bytes and capture date right and staging empty, then only the new frames on a second job (`importsTheCardIntoFilesAndNothingTwice`); a slow catalogue holding the job (`aSlowCatalogueHoldsTheJobUntilItIsListed`); *did suspend* pausing, the download in flight committed, *resumed operations* alone not continuing and the app's return continuing (`didSuspendPausesAndTheAppsReturnContinues`); a removal mid-file, the partial file deleted, and the interrupted file copied again from its start on the replugged link (`aRemovalMidFileWaitsAndTheReplugCopiesItAgainFromItsStart`); busy retried, unreadable skipped, a listing failure retried (`failuresFollowTheirOutcomes`); a short file caught by size and fetched again; phone storage full stopping the job with what was imported kept; Remote Shoot stopping it; two in flight, both at once (9 tests, about 1 s on Linux).

Remaining: the Wi-Fi behaviour comes in Iteration 3 with `IPLink`: Sony's whole-card session (SDIO_Connect, SDIO_OpenSession 0x9210, 0x9212), the plain session's StoreNotAvailable, 0x101B's InvalidObjectHandle in a contents-transfer session and resume with 0x9211, serving the 0xFFFFC001 buffer slot, and the other 0xC2xx events, with the simulator in the PTP/IP flavour and a PTP/IP link against `PTPIPSimulatorServer`. Folder objects (association handles, as the camera's multiples of 0x80000) and the MTP property list (0x9805) aren't served; add them if a test needs them. Faults (drops, a slow link, duplicate file names) are Iteration 2's. CI has yet to run the server's tests in the iOS Simulator; if the loopback-only listener fails there (`start()` throws `listenerFailed`, "waiting: …" when the listener can't listen yet, rather than hanging), the listener's `requiredInterfaceType` is the first thing to look at. `make fixtures` doesn't refresh the simulator's copies (the copy test catches drift). Section 6's *Copy as JPEG* tests run on the simulator's stand-in bytes with a fake JPEG maker (the bytes and thumbnails aren't decodable images); a real render is the bench iPhone's check.

Could change with: the fixtures it replays; the operations the camera actually lists in DeviceInfo. Answered: over PTP/IP the camera doesn't take the standard `GetPartialObject` in a contents-transfer session (0x101B answers InvalidObjectHandle) and resumes with Sony's 0x9211, which the simulator adds in Iteration 3 together with the whole-card session (a plain session answers StoreNotAvailable).
